## 4. 精度、性能与真实性规则

1. 第 5 页：精度是前置门槛，先达标再验收。基线统一取官方 GPU 结果。满分指标按满分计算 2% 容差，例如百分制为 2 pt、OCRBench 千分制为 20 分；WER、FID、时间戳偏移等按基线值的 2% 计算。
2. 第 5、8、13 页：官方 baseline 固定 greedy、思考开关、max_tokens、数据子集与题数，参赛者不允许修改。`baselines/` 和官方 `data/` 原样保留。
3. 第 5 页：干净环境一键复跑，偏差大于 20% 打回。PDF 没有进一步说明该 20% 覆盖哪些统计量，需要提交模板或官方解释。
4. 第 5 页：支持 INT8 / INT4 等量化，异构卡不支持 FP8 / FP4 / MXFP4；量化版本单独计件，须注明方法与工具，精度口径相同。
5. 第 5、14 页：首次提交必须附性能实测，并将其作为该件性能基准。后续在同卡型、同框架、同负载下提升 ≥10% 的优化另计费。
6. 第 6 页：禁止改权重（申报量化除外）、结构、tokenizer、采样语义来规避计算；禁止硬编码答案、伪造日志，违反即取消资格。
7. 第 7 页：报告版本、精度分数、性能数字必须与 `env.log`、`verify_result.json`、`bench/round2.jsonl` 一致，原始文件不得删减。

## 5. 性能脚本规定

第 7、14、15 页给出的文本 / 多模态理解压测口径如下：

- 输入长度为 4096、16384，输出长度为 1024。
- 每个输入长度分别测试并发 1、8、64，共六档。
- 每档连续测试两次，第一次预热，第二次计分；两轮结果均保存。
- 每档请求数为并发的两倍，最低 8 条，即 8、16、128。
- `--seed 1`，`--random-range-ratio 1`。
- 统一使用 SGLang serving benchmark 客户端测试 SGLang / vLLM 服务。
- T02 多模态理解使用 `BENCH_MODE=image bash bench.sh`，每请求一张图；示例分辨率为 `1080p`，但明确以分题材料为准。
- 保存 `bench/round1.jsonl`、`bench/round2.jsonl`、各档日志、`bench/summary.md`。
- 某档失败需保留日志，在报告“注意事项”中说明；PDF 没有授权隐藏失败档位或缩短负载后仍声称完成六档。

报告汇总字段包括完成请求数、耗时、请求吞吐、输出吞吐、总吞吐、平均 / P99 TTFT、平均 / P99 TPOT、平均端到端延迟（第 14 页）。

## 6. 交付结构、流程与报告八章

第 6 页规定：提交一份技术报告加一个代码仓库；报告按官方八章模板作为 `README.md`；报告使用的镜像提交 SCNet 镜像库，代码提交光合开发者社区代码托管；平台每周五验收（第 1 页）。首次验收通过计 1000 元 / 件，优化独立计费（第 1 页）。

| 报告章节 | 所需内容与证据 | 页码 |
|---|---|---|
| 1. 简介 | 模型 × 卡型 × 框架 × 精度，模型介绍，与官方部署差异，仓库结构与一键复现命令 | 第 7 页 |
| 2. 验证环境 | 镜像完整地址含 tag，DTK / torch / triton / 框架 / DAS / transformers / flash-attn 等版本；卡型、卡数、模型路径、端口、Notebook 区域与规格；以 `env.log` 为证 | 第 7、9、10 页 |
| 3. 适配优化方案 | 原镜像、包版本升级及原因、安装方式、代码 patch 及原因、精度影响；没有改动就如实说明 | 第 7、9 页 |
| 4. 服务启动脚本 | `env.sh`、`run.sh`、最终展开命令、并行 / 上下文 / 显存 / parser / 图模式 / 必要环境变量等参数理由，保留 `server.log` | 第 7、8、10、11 页 |
| 5. Smoke 测试 | `/health`、`/v1/models`、问答与适用的多轮 / 流式；T02 另须证明单图 / 多图正常；保留 `smoke.log` | 第 2、7、11 页 |
| 6. 精度测评 | 官方数据集、子集题数、解码、思考开关、判分；`verify_result.json` 对照官方 GPU 基线 | 第 7、12、13 页 |
| 7. 性能参考 | 固定六档，两轮取第二轮，附完整原始文件与汇总表 | 第 7、14、15 页 |
| 8. 注意事项 | 不支持的开发档位、模型参数变动原因与影响依据、已知限制、踩坑与规避 | 第 7 页 |

仓库需包含：`README.md`、`env.sh`、`env_check.sh`、`run.sh`、`smoke.sh`、`verify.py`、`bench.sh`、官方 `baselines/`、官方 `data/`、`bench/`。有新增依赖时加入锁定版本的 `requirements-extra.txt`；有代码改动时加入顺序编号 `patches/*.patch`（第 7、8 页）。

第 9 页规定 `requirements-extra.txt` 使用 `--no-deps` 安装，避免依赖解析把国产异构版 torch 替换成 CUDA 版；连带依赖须逐项固定。第 10 页要求补丁按顺序重放，打不上直接失败；重复执行应跳过已应用补丁。第 11 页要求轮询健康检查与进程存活，上限由 `LOAD_TIMEOUT` 指定，避免固定等待掩盖失败。

第 15 页规定提交前执行 `python verify.py --selfcheck`。实际验证顺序为：

```bash
bash run.sh
bash env_check.sh
bash smoke.sh
source env.sh && python verify.py
BENCH_MODE=image bash bench.sh
```

各步产物应与报告一起保留，不能用本地静态检查或自创 smoke 代替正式精度 / 性能实测。
